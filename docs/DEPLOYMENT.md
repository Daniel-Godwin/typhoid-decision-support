# Deployment Guide — Render

Follow these steps in order. Each one is a single action.

---

## Before you start

You need a GitHub account and a Render account (both free). The repository must
contain `models/*.joblib` — the application will not serve predictions without
them. They total about 19 MB, which is within GitHub's limits.

---

## Step 1 — Put the project on GitHub

From the project folder:

```powershell
git init
git add .
git commit -m "Typhoid decision support system"
git branch -M main
git remote add origin https://github.com/<your-username>/typhoid-decision-support.git
git push -u origin main
```

Confirm on GitHub that `models/` contains the four `.joblib` files. `.gitignore`
excludes `instance/`, `logs/` and `.env`, which is correct — it does **not**
exclude the models.

---

## Step 2 — Create the Render service

1. Sign in at https://render.com
2. Click **New** → **Blueprint**
3. Connect your GitHub account and select the repository
4. Render reads `render.yaml` and proposes a web service plus a PostgreSQL
   database. Click **Apply**

`render.yaml` already sets the runtime, build command, start command, health
check path and every non-secret environment variable, and wires `DATABASE_URL`
from the database automatically.

---

## Step 3 — Set the two secrets

In the Render dashboard, open the service → **Environment**, and add:

| Key | Value |
|---|---|
| `BOOTSTRAP_ADMIN_EMAIL` | your administrator email address |
| `BOOTSTRAP_ADMIN_PASSWORD` | a strong temporary password, at least 10 characters with letters and digits |

`SECRET_KEY` is generated by Render automatically. Do not set it by hand.

Click **Save Changes**. Render redeploys.

---

## Step 4 — Watch the first deploy

Open the **Logs** tab. A successful start-up prints, in order:

```
Database tables are present.
Administrator created: <your email>
logging configured env=production level=INFO destination=stdout
model preload: {'binary': 'loaded', 'multiclass': 'loaded'}
application ready name=Typhoid Diagnostic Decision Support version=2.0.0 env=production
```

`preDeployCommand` runs `flask bootstrap`, which creates the tables and the first
administrator. It is idempotent, so it is safe on every subsequent deploy.

---

## Step 5 — Verify

Open `https://<your-service>.onrender.com/health`. You should see:

```json
{
  "status": "ok",
  "environment": "production",
  "version": "2.0.0",
  "checks": {
    "database": "ok",
    "models": {"binary": "available", "multiclass": "available"}
  }
}
```

If `status` is `degraded`, the `checks` block names what is wrong.

---

## Step 6 — First sign-in

Go to `https://<your-service>.onrender.com/auth/login` and sign in with the
bootstrap administrator credentials. You will be required to set a new password
before anything else — this is enforced, not optional.

Then create the clinician accounts from **Administration → User accounts → Add user**.

---

## Free-plan behaviour to expect

The free web service sleeps after 15 minutes of inactivity, so the first request
after a quiet period takes roughly 30–50 seconds while the container starts and
the models load. Subsequent requests are fast. If you are demonstrating the
system live, open it a minute beforehand.

The free PostgreSQL database expires after 90 days. Note the date if the
deployment needs to survive past your defence.

---

## Verifying the twelve areas in production

Once deployed, work through this checklist and record the result:

| # | Area | How to verify |
|---|---|---|
| 1 | Authentication | Sign in; try a wrong password five times and confirm the lockout |
| 2 | Authorisation | Sign in as a clinician, open `/admin/users`, expect 403 |
| 3 | Admin functions | Create a user, disable it, unlock it, view the activity log |
| 4 | Clinician functions | Register a patient, run an assessment, open its detail page |
| 5 | Database | Confirm the assessment appears after a page reload |
| 6 | Patient management | Search the patient register; try a duplicate patient code |
| 7 | Model loading | `/health` reports both models available; `/admin/system` shows kernel and training date |
| 8 | Preprocessing | Submit an assessment leaving the three optional fields as "Not recorded" |
| 9 | Prediction results | Check the probability, the triage recommendation and the contribution chart |
| 10 | Logging | `/admin/logs` shows login, prediction_created and access_denied entries |
| 11 | Errors and validation | Visit a non-existent URL; submit the assessment form with a blank required field |
| 12 | Responsive UI | Open the site on a phone; confirm the navigation drawer and single-column forms |

## Environment variables

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `SECRET_KEY` | yes | — | Session signing. Render generates it |
| `DATABASE_URL` | yes | SQLite fallback | PostgreSQL connection. Wired automatically |
| `FLASK_ENV` | yes | development | Set to `production` |
| `BOOTSTRAP_ADMIN_EMAIL` | first deploy | — | Initial administrator |
| `BOOTSTRAP_ADMIN_PASSWORD` | first deploy | generated | Initial password; must be changed at first sign-in |
| `LOG_TO_STDOUT` | no | true in production | Render captures stdout |
| `LOG_LEVEL` | no | INFO | DEBUG, INFO, WARNING, ERROR |
| `TRIAGE_THRESHOLD` | no | 0.08 | Probability at which a case is flagged for confirmatory testing. Derived in `reports/THRESHOLD_ANALYSIS.md`; regenerate after any retraining |
| `DEFAULT_TARGET_MODE` | no | binary | `binary` or `multiclass` |
| `DEFAULT_FEATURE_POLICY` | no | routine | `routine`, `clinical_only`, `no_fever_duration` |
| `SESSION_LIFETIME_MINUTES` | no | 60 | Idle session timeout |
| `LOGIN_MAX_ATTEMPTS` | no | 5 | Failures before lockout |
| `LOGIN_LOCKOUT_MINUTES` | no | 15 | Lockout duration |
| `RATELIMIT_ENABLED` | no | true | Rate limiting on sensitive routes |

`postgres://` URLs are rewritten to `postgresql+psycopg2://` automatically, so
Render's connection string works unchanged.

## Troubleshooting

**Build fails on `psycopg2-binary`** — confirm `PYTHON_VERSION` is `3.12.6`.
Version 3.13 has known wheel gaps for some dependencies.

**`model_unavailable` in the logs** — the `.joblib` files were not committed.
Check `git ls-files models/`.

**`ModuleNotFoundError: typhoid_ml`** — `PYTHONPATH` must include the `src`
directory. `render.yaml` sets it to `/opt/render/project/src/src`, which is
correct for Render's checkout layout.

**Redirect loop at sign-in** — `SECRET_KEY` is changing between restarts. Ensure
it is set as an environment variable rather than generated at run time.

**Everything works but sign-in fails silently** — check `SESSION_COOKIE_SECURE`.
It is `True` in production, so the site must be served over HTTPS. Render does
this by default.

## Running locally

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

$env:FLASK_APP = "run_dev.py"
python -m flask init-db
python -m flask seed-demo
python run_dev.py
```

Open http://127.0.0.1:5000 and sign in with `admin@example.com` / `AdminPass2026`.

To run the production stack locally exactly as Render does:

```powershell
$env:FLASK_ENV = "production"
$env:SECRET_KEY = "any-long-random-string"
$env:BOOTSTRAP_ADMIN_EMAIL = "admin@example.com"
$env:BOOTSTRAP_ADMIN_PASSWORD = "ProdAdmin2026x"
python -m flask bootstrap
gunicorn wsgi:app --workers 2 --threads 4
```

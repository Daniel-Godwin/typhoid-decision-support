# Deployment Guide — Render

Follow these steps in order. Each one is a single action.

The blueprint is sized for Render's **free** compute plan (0.1 CPU, 512 MB RAM).
Three details of that plan shape the configuration, and are worth knowing before
you start:

| Constraint | Consequence here |
|---|---|
| 512 MB RAM | One gunicorn worker only. The process holds pandas, scikit-learn and the model and measures ~240 MB; two workers would be OOM-killed |
| Pre-deploy commands are paid-only | `flask bootstrap` runs from the **start command** instead. It is idempotent, so running it on every start is safe |
| One free PostgreSQL per workspace, expiring after 30 days | The database is **external**. `render.yaml` declares no database and takes `DATABASE_URL` as a secret instead |

The service also sleeps after 15 minutes without traffic, and the free tier
allows 750 instance-hours per month across the workspace.

### Why the database is external

Render permits a single free Postgres per workspace, so a second project cannot
provision one — the blueprint fails with *"cannot have more than one active free
tier database"* and cancels the web service along with it. Render's free
Postgres also expires 30 days after creation, which is shorter than most
projects need.

Any hosted Postgres works. These instructions use Neon's free plan: 0.5 GB of
storage, no expiry, and 100 compute-hours a month. It suspends after five
minutes idle and wakes on the next connection, which is why
`SQLALCHEMY_ENGINE_OPTIONS` sets `pool_pre_ping` and a 280-second
`pool_recycle` — together they discard a connection the provider has already
closed, rather than failing the first request after a quiet period.

## Before you start

You need a GitHub account and a Render account, both free.

The repository must contain `models/*.joblib` — the application builds cleanly
without them and then reports `model_unavailable` on every prediction. They
total about 19 MB, which is well inside GitHub's limits. `.gitignore` is written
to keep them; do not "tidy" them out.

---

## Step 1 — Put the project on GitHub

From the project folder:

```powershell
git init
git add .
git commit -m "Typhoid diagnostic decision support system"
git branch -M main
git remote add origin https://github.com/<your-username>/typhoid-decision-support.git
git push -u origin main
```

Then confirm the models were committed:

```powershell
git ls-files models/
```

You should see four `.joblib` files. If that command prints nothing, stop — the
deployment will not work. Check `.gitignore`.

---

## Step 2 — Create the database

1. Sign in at https://neon.com and create a project
2. Name the database `typhoid` and choose a region near your Render region
   (`frankfurt` in the blueprint — pick an EU region for both)
3. Copy the **connection string**. It looks like:

```
postgresql://user:password@ep-something.eu-central-1.aws.neon.tech/typhoid?sslmode=require
```

Keep the `?sslmode=require` — removing it disables TLS. The application rewrites
`postgresql://` to `postgresql+psycopg2://` at start-up and preserves the query
string, so paste the string exactly as the provider gives it.

Treat that string as a credential: it contains the database password. Do not
commit it, and do not paste it into a chat, an issue or a screenshot.

---

## Step 3 — Create the Render service

1. Sign in at https://render.com
2. Click **New** → **Blueprint**
3. Connect your GitHub account and select the repository
4. Render reads `render.yaml` and proposes a single web service

Render then prompts for the three values marked `sync: false`:

| Key | Value |
|---|---|
| `DATABASE_URL` | the connection string from Step 2 |
| `BOOTSTRAP_ADMIN_EMAIL` | your administrator email address |
| `BOOTSTRAP_ADMIN_PASSWORD` | a temporary password: at least 10 characters, with a letter and a number |

The bootstrap password is temporary by design — the application forces a change
at first sign-in and blocks every other page until it is done.

`SECRET_KEY` is generated by Render and kept for the life of the service. Do not
set it by hand, and do not regenerate it — every session is invalidated if it
changes.

Click **Apply**.

---

## Step 4 — Watch the first deploy

Open the **Logs** tab. A successful start-up prints, in order:

```
logging configured env=production level=INFO destination=stdout
model preload: {'binary': 'loaded'}
application ready name=Typhoid Diagnostic Decision Support version=2.0.0 env=production
Database tables are present.
Administrator created: <your email>
[INFO] Starting gunicorn
[INFO] Listening at: http://0.0.0.0:10000
```

The first three lines appear twice: once for the `flask bootstrap` process and
once for the gunicorn worker. That is expected.

On 0.1 CPU the build takes roughly 3–6 minutes and the first boot 60–90 seconds.

---

## Step 5 — Verify

Open `https://<your-service>.onrender.com/health`. You should see:

```json
{
  "status": "ok",
  "environment": "production",
  "version": "2.0.0",
  "checks": {
    "database": "ok",
    "database_engine": "postgresql",
    "models": {"binary": "available", "multiclass": "available"}
  }
}
```

**Check `database_engine` says `postgresql`.** If it says `sqlite`, `DATABASE_URL`
did not reach the service and the application is running on an ephemeral local
file: it will behave correctly until the service sleeps or redeploys, and then
every stored patient and assessment is gone. In production that state returns
HTTP 503 with `status: degraded` and a `database_warning` naming the problem.

If `status` is `degraded`, the `checks` block names what is wrong.

---

## Step 6 — First sign-in

Go to `https://<your-service>.onrender.com/auth/login` and sign in with the
bootstrap administrator credentials. You will be required to set a new password
before anything else — this is enforced, not optional.

Then create the clinician and auditor accounts from
**Administration → User accounts → Add user**.

---

## Step 7 — Prepare it for a reviewer

Before sending the link on:

1. Create a clinician account for the reviewer with a temporary password. Do not
   give them the administrator account — the point of the role separation is
   that it can be demonstrated.
2. Register two or three patients so the register is not empty.
3. Run one assessment so the dashboard and the activity log have content.
4. Open the site a minute before they do. A sleeping free service takes about a
   minute to wake, and a reviewer who meets a loading page first will assume the
   deployment is broken.
5. Send them the URL, the credentials, and the note that the first load is slow.

---

## Verifying the twelve areas in production

Work through this checklist on the deployed site and record the result:

| # | Area | How to verify |
|---|---|---|
| 1 | Authentication | Sign in; try a wrong password five times and confirm the lockout |
| 2 | Authorisation | Sign in as a clinician, open `/admin/users`, expect 403 |
| 3 | Admin functions | Create a user, disable it, unlock it, view the activity log |
| 4 | Clinician functions | Register a patient, run an assessment, open its detail page |
| 5 | Database | Confirm the assessment appears after a page reload |
| 6 | Patient management | Search the patient register; try a duplicate patient code |
| 7 | Model loading | `/health` reports both models available; `/admin/system` shows kernel and training date |
| 8 | Preprocessing | Submit an assessment leaving the three optional fields as "Not recorded" |
| 9 | Prediction results | Check the probability, the triage recommendation and the contribution chart |
| 10 | Logging | `/admin/logs` shows login, prediction_created and access_denied entries |
| 11 | Errors and validation | Visit a non-existent URL; submit the assessment form with a blank required field |
| 12 | Responsive UI | Open the site on a phone; confirm the navigation drawer and single-column forms |

## Environment variables

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `SECRET_KEY` | yes | — | Session signing. Render generates it |
| `DATABASE_URL` | yes | SQLite fallback | PostgreSQL connection. Wired automatically |
| `FLASK_ENV` | yes | development | Set to `production` |
| `FLASK_APP` | yes | — | `wsgi.py`, so the start command can run `flask bootstrap` |
| `PYTHONPATH` | yes | — | Must include the `src` directory |
| `BOOTSTRAP_ADMIN_EMAIL` | first deploy | — | Initial administrator |
| `BOOTSTRAP_ADMIN_PASSWORD` | first deploy | generated | Initial password; must be changed at first sign-in |
| `LOG_TO_STDOUT` | no | true in production | Render captures stdout |
| `LOG_LEVEL` | no | INFO | DEBUG, INFO, WARNING, ERROR |
| `TRIAGE_THRESHOLD` | no | 0.08 | Probability at which a case is flagged for confirmatory testing. Derived in `reports/THRESHOLD_ANALYSIS.md`; regenerate after any retraining |
| `DEFAULT_TARGET_MODE` | no | binary | `binary` or `multiclass` |
| `DEFAULT_FEATURE_POLICY` | no | routine | `routine`, `clinical_only`, `no_fever_duration` |
| `PRELOAD_MODELS` | no | true | Load the default model at start-up |
| `PRELOAD_ALL_MODELS` | no | false | Load every model at start-up. Leave off on the free plan |
| `SESSION_LIFETIME_MINUTES` | no | 60 | Idle session timeout |
| `LOGIN_MAX_ATTEMPTS` | no | 5 | Failures before lockout |
| `LOGIN_LOCKOUT_MINUTES` | no | 15 | Lockout duration |
| `RATELIMIT_ENABLED` | no | true | Rate limiting on sensitive routes |

`postgres://` URLs are rewritten to `postgresql+psycopg2://` automatically, so
Render's connection string works unchanged.

## Troubleshooting

**`model_unavailable` in the logs** — the `.joblib` files were not committed.
Run `git ls-files models/`; if it prints nothing, check `.gitignore`, then
`git add -f models/*.joblib` and push.

**Service is killed and restarted repeatedly, or "Ran out of memory"** — more
than one gunicorn worker on the free plan. The process measures ~240 MB; keep
`--workers 1` and raise concurrency with `--threads` instead. Do not set
`PRELOAD_ALL_MODELS=true` on 512 MB.

**`ModuleNotFoundError: typhoid_ml`** — `PYTHONPATH` must include the `src`
directory. `render.yaml` sets it to `/opt/render/project/src/src`, which is
correct for Render's checkout layout.

**Tables missing, or "no such table: users"** — `flask bootstrap` did not run.
It belongs in the start command, not `preDeployCommand`, which requires a paid
instance type. Check that `FLASK_APP=wsgi.py` is set.

**"cannot have more than one active free tier database"** — a `databases:` block
in `render.yaml` while the workspace already has a free Postgres. The blueprint
here declares none; the database is external, supplied through `DATABASE_URL`.

**`OperationalError: SSL connection has been closed unexpectedly`** — the
external database suspended while idle and the pooled connection went stale.
`pool_pre_ping` handles this; if it appears, confirm `SQLALCHEMY_ENGINE_OPTIONS`
still sets `pool_pre_ping` and `pool_recycle`.

**`connection to server ... failed: SSL error`** — `?sslmode=require` was
stripped from `DATABASE_URL`. Paste the provider's string unedited.

**`FATAL: password authentication failed`** — the password in the connection
string is stale, or the pooled and direct variants were mixed. Copy it again
from the provider's dashboard.

**Build fails on `psycopg2-binary`** — confirm `PYTHON_VERSION` is `3.12.6`.
Later versions have wheel gaps for some dependencies.

**Redirect loop at sign-in** — `SECRET_KEY` is changing between restarts. It must
be an environment variable, not generated at run time.

**Everything works but sign-in fails silently** — `SESSION_COOKIE_SECURE` is
`True` in production, so the cookie is only set over HTTPS. Render serves HTTPS
by default; this bites only when testing the production config over plain HTTP
locally.

**HTTP 502 Bad Gateway on the first request** — this is almost always the free
service waking from sleep, not a crash. Render returns 502 while the container
boots and no worker is yet listening. Wait 60 to 90 seconds and reload.

To tell a cold start from a real failure, open the service's **Events** tab. A
cold start shows no new event; a genuine failure shows *Exited with status 1*,
*Out of memory*, or a failed deploy. `/health` returning `status: ok` after the
wait confirms the service itself is sound.

The start command runs `flask bootstrap` with `PRELOAD_MODELS=false`, because
that step only touches the database. Loading the model there would import
pandas and scikit-learn a second time before gunicorn even starts, roughly
doubling the cold-start delay on 0.1 CPU.

**First request takes a minute** — expected. The free service sleeps after 15
minutes of inactivity.

## Running locally

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

$env:FLASK_APP = "run_dev.py"
python -m flask init-db
python -m flask seed-demo
python run_dev.py
```
